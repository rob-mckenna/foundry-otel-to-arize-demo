# Project Context

- **Owner:** Rob McKenna
- **Project:** foundry-otel-to-arize-demo — a reusable observability demo repository showing how to instrument Microsoft Foundry Prompt Agents with OpenTelemetry/OpenInference, capture telemetry in Application Insights, export it through a transformation pipeline, and visualize/correlate traces and token usage in Arize. Built to be reused across enterprise healthcare customers (UnitedHealth Group, CVS Health, Elevance Health, etc.) evaluating observability for Foundry Prompt Agents.
- **Stack:** Azure (Foundry, Application Insights, Log Analytics, Event Hub, Azure Functions, Key Vault, managed identities), Infrastructure-as-Code (Bicep/Terraform), OpenTelemetry + OpenInference semantic conventions, Arize OTLP ingestion
- **Created:** 2026-10-02

## Learnings

<!-- Append new learnings below. Each entry is something lasting about the project. -->
- Telemetry Mapping issues require the full chain: App Insights source record → Azure Monitor field → OTel field → OpenInference attribute → Arize destination field → transformation logic → correlation requirements → validation query.
- Current-state pipeline (App Insights → Event Hub → Function → Arize OTLP) must stay documented separately from the future-state direct-OTLP design.
- Milestone 2 first pass (#32–#37): this sandbox has no Python interpreter and no live Azure resources — every "validated" claim had to be split into (a) what in-memory `InMemorySpanExporter` + direct source inspection actually proved, vs. (b) what's "documented, pending live instance/infra merge." Never claim a test passed without actually running it; say plainly when an environment can't execute what it wrote, and let a human/CI re-run it.
- App Insights `operation_Id`/`operation_ParentId`/`id` are already the exact same byte-width as OTel `trace_id`/`parent_span_id`/`span_id` — no hex-padding/conversion is needed between them, only "does the value survive each hop unchanged." The real correlation risk is entirely in Event Hub partition-key choice and Function batch-checkpointing strategy, not format translation — flagged to Infra before #17/#19 are implemented rather than discovered as a bug after.
- `customDimensions` values are exported from App Insights as strings regardless of the OTel SDK's original attribute type (int/bool) — every downstream Azure Function field mapping must explicitly re-cast, or numeric/boolean fields silently become quoted strings in Arize. This is the single highest-risk correctness bug class in the whole transform step.
- Issues referencing attributes the agent doesn't actually emit (e.g. #32 listed `llm.input_messages`/`llm.output_messages`, but the agent only sets `input.value`/`output.value`) should be documented as an explicit current-state gap against real source, never silently assumed into existence to match the issue text.
- Grouped near-duplicate `telemetry-mapping.yml` issues by shared transformation logic (identity/correlation, token, LLM I/O, span-kind/status — 4 issues instead of 11+ one-per-attribute) and recorded the rationale directly in the mapping doc so a reviewer doesn't wonder why there aren't more issues.
- 2026-10-03: Delivered all 10 Milestone 3 (Arize Integration) issues (#89, #90, #91, #92, #38, #39, #40, #41, #42, #43) as 10 separate PRs (#110, #112, #113, #114, #115, #116, #117, #118, #119, #120), each in its own dedicated `.worktrees/telemetry-<N>` worktree/branch, removed immediately after each PR opened — worktree isolation again prevented any shared-checkout file races, even with other squad agents' concurrent worktrees (`agent-24..31`) present in the same repo throughout this pass. Key findings:
  1. **The #36 field-mapping grouping rationale (4 groups instead of 11+ per-field issues) paid off directly at doc-writing time.** Each of #89-#92's issue body already contained the full field-level detail from the Milestone 2 pass (source record → Azure Monitor field → OTel field → OpenInference attribute → Arize destination → transformation logic → correlation requirements → validation query → acceptance criteria) — this milestone's work was formalizing that content as standing docs under `docs/telemetry/mapping/*.md` (not just issue text) and cross-linking them from the already-merged `field-mapping.md`/`trace-correlation-preservation.md`, which already referenced #89-#92 by number.
  2. **Deliberately avoided editing any shared file (`field-mapping.md`, `trace-correlation-preservation.md`) across the 10 parallel-branched PRs** — every deliverable is a brand-new file or a new file in a new subdirectory (`docs/telemetry/mapping/`, `docs/telemetry/kql/`). New files never conflict regardless of merge order, sidestepping the "parallel branches editing the same file with no common ancestor" conflict Infra documented for `main.bicep` in Milestone 1. None of these 10 PRs need to merge in any particular sequence.
  3. **No Python interpreter and no live Azure/Arize environment, same as Milestone 2.** `src/telemetry-pipeline/` is still a placeholder (no Function transform code exists yet, even though the Function App *infra shell* from #19 is now merged), so #38's OTLP conformance test (`tests/export/test_otlp_export_conformance.py`) is explicitly a reference-transform scaffold proving the mapping specs are internally consistent — not a test of production code — and, like the Milestone 2 token-usage test, could not actually be executed in this sandbox. Every one of the 10 docs carries an explicit "Validated-via-review" vs. "Requires live-environment re-verification" split so a doc-only PR never implies something was live-tested.
  4. **Dependency ordering matters for doc cross-references, not just build correctness.** Did #89-#92 and #41 first (no dependencies on other Milestone 3 work), then #38 (feeds #39/#40), then #39, then #40, then #42 (needs #39), then #43 (needs #40+#41) — so every later doc could link forward to an already-written (if not yet merged) sibling doc instead of a bare issue number.
  - Flagged the standing gap (no live validation executed for any of Milestone 3's acceptance criteria) to `.squad/decisions/inbox/telemetry-milestone-3-arize-integration.md` for Scribe to merge — whoever implements #19's actual Function transform code should treat these 10 docs as the build spec, not as already-validated results.
- 2026-10-03 (same day, follow-up batch): Delivered the Milestone 4 "Customer Demo Readiness" validation batch — 9 issues (#50-#58) plus a drift-fix PR, 10 PRs total (#121-#129, #131), using the same worktree-per-issue pattern. Key findings:
  1. **Confronted a real README-drift + prematurely-closed-issue finding routed by Lead** (`.squad/decisions/inbox/lead-telemetry-pipeline-readme-drift.md`): `src/telemetry-pipeline/README.md` claimed `validated, implemented` status while the directory held zero Function code. Fixed it (PR #121, option 1 — soften the claim, matching `src/prompt-agent/README.md`'s pattern) and, while investigating, found issue #37 itself had been closed (`stateReason: COMPLETED`, zero comments, no linked PR) despite its own acceptance criteria requiring KQL+Arize evidence that doesn't exist anywhere in the repo. **Reopened #37** with an explanatory comment rather than silently accepting a closed-but-unproven issue — a closed GitHub issue is not itself evidence of completion; the actual artifacts (or their absence) are what matter. Don't assume "closed" means "done" when auditing a track you own.
  2. **The prompt-agent track (Milestone 1, issues #24-#31) turned out to already have real, executable-by-design source code and a 16-test pytest suite** (`src/prompt-agent/`), not just specs — discovered this only by actually listing `.py` files instead of assuming "no Python interpreter" meant "no code exists to review." Every M4 validation doc for Telemetry Capture criteria (#50-52, part of #58) could therefore cite *specific, already-written, exact-match-assertion* unit tests as validated-via-review evidence, rather than describing hypothetical future tests — a notably stronger evidence base than Milestone 2/3's doc-only work.
  3. **Clear bimodal split emerged across the 9 issues based on whether the thing being validated is source-side (Prompt Agent) or pipeline-side (Event Hub/Function/Arize):** #50, #51, #52, and part (a) of #58 could be validated-via-review against real existing tests (Pass or Pass-with-caveats). #53, #54, #55, #56, #57, and part (b) of #58 are honestly marked **Blocked**, not "Pass assuming the pipeline works" — because `src/telemetry-pipeline/` has zero implementation and no Arize instance has ever been deployed in this repo's history. Resist the temptation to write a validation doc that sounds complete when the underlying system doesn't exist yet; "Blocked" is a valid and necessary verdict, not a failure to document well.
  4. **A validation pass can surface genuine, fixable-today gaps even when most of the batch is blocked on missing infra.** While validating #58's exporter-observability criterion, found that `telemetry.py`'s `shutdown_tracing()` discards `force_flush()`'s boolean return value and that no export success/failure counter exists anywhere — a real gap requiring no new infrastructure to fix. Filed it as issue #130 rather than just noting it in a doc, per #58's own "document what exists and file a gap issue for anything missing" acceptance criterion — a validation task's job includes surfacing new, actionable issues, not only grading existing acceptance criteria pass/fail.
  5. **Operational note:** when a worktree needs a PR-body scratch file, write it and `git add` the *specific* doc file(s) only — `git add -A` after creating a scratch `pr_body.md` in the same directory will accidentally commit it to the branch (happened once on #51's branch, caught and fixed with a follow-up `git rm --cached` commit before opening the PR). Prefer passing PR bodies inline via `gh pr create --body "..."` for shorter bodies, or write the scratch file, stage only the real deliverable explicitly, and delete the scratch file before any `git add -A`.
