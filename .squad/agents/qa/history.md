# Project Context

- **Owner:** Rob McKenna
- **Project:** foundry-otel-to-arize-demo — a reusable observability demo repository showing how to instrument Microsoft Foundry Prompt Agents with OpenTelemetry/OpenInference, capture telemetry in Application Insights, export it through a transformation pipeline, and visualize/correlate traces and token usage in Arize. Built to be reused across enterprise healthcare customers (UnitedHealth Group, CVS Health, Elevance Health, etc.) evaluating observability for Foundry Prompt Agents.
- **Stack:** Azure (Foundry, Application Insights, Log Analytics, Event Hub, Azure Functions, Key Vault, managed identities), Infrastructure-as-Code (Bicep/Terraform), OpenTelemetry + OpenInference semantic conventions, Arize OTLP ingestion
- **Created:** 2026-10-02

## Learnings

<!-- Append new learnings below. Each entry is something lasting about the project. -->
- Demo validation must use synthetic prompts/data only and capture concrete evidence (trace IDs, query results) — "looked fine" is not an acceptable validation record.
- Documentation updates are part of the same change as any architecture/behavior change, not a separate follow-up task.
- Milestone 4 (demo docs/runbooks/validation-plan track, #48/#44/#45/#46/#47/#59/#61/#62): as of this pass, the Prompt Agent half of the pipeline (invoke, OTel spans, OpenInference attributes, token counts, correlation ID + retry traceability, App Insights capture) is validated end-to-end with captured evidence under `src/prompt-agent/samples/`. The Event Hub → Azure Function transform → Arize export half is **infrastructure-provisioned and fully specified** (`docs/telemetry/field-mapping.md`) but has **no implementation code yet** — `src/telemetry-pipeline/` is still a placeholder README. Every demo doc in this batch (narrative, runbook, fallback, one-pager, README, runbooks, validation plan) had to be written to say this honestly rather than imply a working Arize dashboard; this is the single biggest risk of overclaiming in this repo right now and future agents touching demo/docs content should re-check `docs/validation/demo-validation-plan.md`'s capability table before writing anything that implies Arize ingestion works today.
- This automated environment has no usable Python interpreter (`python`/`py` fail to resolve) and a permission-restricted Azure CLI profile (`PermissionError` on `~/.azure/azureProfile.json`) — any "dry-run"/"execute verbatim" acceptance criterion in an issue cannot actually be run live from here. Document this limitation explicitly in the PR (static verification instead, with a named follow-up) rather than silently claiming a live run happened — this matches the same limitation Infra already recorded for `az deployment ... what-if`.
- For the doc-drift checklist (#62), the issue explicitly said "coordinate with whoever owns the PR template — do not edit it directly." Pattern for this: write the standalone doc/checklist, link to it from README, and leave the actual PR-template edit as an explicit ask recorded in the `.squad/decisions/inbox/` drop file for Lead/Scribe to action, rather than touching `.github/pull_request_template.md` directly even though it would have been easy to do so.
- When other agents' PRs for the same milestone haven't merged yet, it's fine (and expected per the task's sequencing note) to add cross-links to files that don't exist on `main` yet (e.g. `demo/narrative.md` from `README.md` before #44 merged) — call this out explicitly in the PR body as a "final cross-link pass needed once everything merges" rather than blocking on merge order.
