- 2026-10-02: Delivered all 5 Milestone 1 Foundation infra issues (#15 Foundry project, #16 App Insights/Log Analytics, #18 Key Vault + managed identity, #20 naming/tagging enforcement, #21 network requirements) as PRs #66/#69/#71/#72/#74, each Bicep-only under `/infra/modules/`, each tagged via a shared `naming.bicep` (compile-time `@export()` helpers) and verified with a dependency-free `infra/scripts/validate-naming.ps1`. Two environment learnings worth remembering for next time:
  1. **The shared working-copy concurrency hazard is real and destructive.** This repo's working directory is used concurrently by multiple squad agents (Lead, Scribe, etc.) who `git checkout` different branches between my tool calls, which silently moved HEAD out from under me mid-task and caused at least one commit to land on the wrong branch. Fix: use `git worktree add .worktrees\<name> -b <branch> origin/main` (worktrees must live *inside* the repo tree — paths outside it hit sandbox `Permission denied`) for every branch touched, and always branch from a freshly-fetched `origin/main`, never the shared local `main` (which can silently drift/diverge from a concurrent agent's unpushed commit). Do all git/file operations for that branch from inside its dedicated worktree directory, never the main checkout.
  2. **`gh`/git in this environment lacks the `workflow` OAuth scope** — pushing any `.github/workflows/*.yml` file is rejected (`refusing to allow an OAuth App to create or update workflow ... without 'workflow' scope`). When a CI-wiring acceptance criterion can't be met for this reason, strip the workflow file and document the equivalent manual pre-merge step instead (most issue acceptance criteria in this repo already anticipate that fallback explicitly).
  3. `az` CLI and a standalone `bicep` binary are both unusable in this sandbox (`az` hits a `PermissionError` reading the cached profile at `~/.azure/azureProfile.json`; no `bicep.exe` is installed) — every Bicep PR in this milestone had to be validated by manual syntax review only, with `az bicep build` / `az deployment group what-if` / live deploy+teardown flagged as a reviewer action item in "Current Limitations" rather than run directly.
- 2026-10-03: Consolidated the 4 remaining Milestone 1 infra PRs (#69 App Insights, #71 Key Vault, #72 naming/tagging, #74 networking) into main one at a time, in that order, after they all drifted from the same pre-#66 base and each had independently rewritten `infra/main.bicep` end-to-end (some even "carried forward" a full imagined snapshot of sibling issues' modules, e.g. #72/#74 branches already contained their own copies of #15/#16/#18's module files). Two lasting lessons:
  1. **Parallel branches off the same base editing the same IaC entry-point file (`main.bicep`) is the root cause, and it compounds.** Every `module`/`param`/`output` block landed as an "add/add" conflict at merge time even for file paths that were never touched by more than one PR, because git had no common ancestor content to diff against. The actual *content* conflicts were almost always trivially combinable (verified via `git diff <mainBlobSHA> <branchBlobSHA> -- <path>` before touching anything) — the pain was 100% structural/mechanical, not semantic. Going forward: either (a) require every infra PR to branch from a freshly-fetched `main` *after* the previous infra PR in the queue has merged (serialize the queue, don't parallelize), or (b) adopt an explicit convention that only one PR at a time "owns" `main.bicep`'s structure (adding new `module`/`output` blocks) and all others are strictly additive new files under `infra/modules/` with zero `main.bicep` edits, reconciled into `main.bicep` by whoever currently owns it.
  2. **A second agent's "fix" merge can silently regress a just-merged PR if the two merges race within seconds.** PR #70 (ADR docs, unrelated issue #13) merged 4 seconds after PR #69 and its own conflict-resolution commit — reasonably, from its branch's point of view — reset `infra/main.bicep`/`main.parameters.json`/`README.md` and deleted `infra/modules/app-insights.bicep` entirely, believing it was removing "accidental cross-contamination" from a shared non-worktree checkout, when in fact that content was PR #69's legitimate, already-merged change. I had to re-detect this by independently diffing `origin/main`'s tree against the PR's own merge commit (not trusting "already merged" status) and push a direct restoring commit to `main` before continuing the queue. Recommendation: after merging any infra PR, re-verify `origin/main`'s actual tree contents (not just PR merge status) before starting the next PR's conflict resolution — another concurrent agent may have merged in between and silently clobbered it.
- 2026-10-03: Delivered Milestone 2's first two infra issues, #17 (Event Hub, PR #83) and #19 (Function App, PR #86), each in its own dedicated worktree (`.worktrees/infra-17`, `.worktrees/infra-19`) per the "Mandatory Worktree Isolation" directive, removed after each PR opened, branches kept. **Worktree isolation fully prevented the Milestone-1-style shared-checkout file races this time** — no HEAD got silently moved out from under me, no commit landed on the wrong branch, and both branches/worktrees coexisted cleanly even while other squad agents (Agent, Telemetry) had ~14 of their own worktrees open concurrently in the same repo (`agent-24..31`, `telemetry-32..37`). Two follow-on refinements to the Milestone-1 `main.bicep` lesson, applied proactively rather than learned the hard way this time:
  1. **I could not actually satisfy "finish and merge #17 before starting #19" literally** — the general instruction not to self-merge takes precedence, and PR review/merge is a human/reviewer action, not mine to perform. Resolution: decoupled the two modules so #19 doesn't *require* #17 to be merged — `function-app.bicep` takes `eventHubNamespaceFqdn`/`eventHubNamespaceResourceId` as plain string parameters (defaulting to empty, wired via the same two-phase cross-wire pattern as `key-vault.bicep`'s `readerPrincipalIds`) rather than consuming `event-hub.bicep` as a sibling module reference. This let #19's worktree branch cleanly from `origin/main` (not from #17's branch) with zero dependency on #17's merge timing.
  2. **Applied the "only one PR owns `main.bicep`'s structure at a time" rule to my own sequential work, not just to parallel agents.** #17 (opened first) wired its new module block + outputs into `main.bicep`/both `main.parameters*.json` as normal. For #19, since #17's PR was still open/unmerged (not yet part of `origin/main`), I deliberately made #19 **additive-only** — `infra/modules/function-app.bicep` plus a `infra/README.md` section — and explicitly did not touch `main.bicep`, documenting in both the README and the PR description that wiring `functionApp` into `main.bicep` (and the `eventHub.receiverPrincipalIds`/`keyVault.readerPrincipalIds` cross-wire) is a deliberate fast-follow once both PRs land. This avoids recreating the exact "both branches independently rewrite `main.bicep`'s structure with no common ancestor" conflict documented above, at the cost of #19 not being deployable end-to-end from its own branch alone (acceptable for a review-stage PR; called out explicitly as a Current Limitation).
  - `az`/`bicep` CLI were still unavailable in this sandbox (same `PermissionError` on `~/.azure/azureProfile.json`, no `bicep.exe`) — both PRs again relied on `infra/scripts/validate-naming.ps1` (passing) plus manual syntax review, flagged identically in each PR's "Tests Performed"/"Current Limitations" sections.
- 2026-10-03: Rebased PR #86 (#19, Function App) onto `main` after PR #83 (#17, Event Hub) merged and the branch went CONFLICTING/DIRTY, then completed the previously-deferred `main.bicep` wiring, all from a fresh dedicated worktree (`.worktrees/infra-19-rebase`, checked out on the *existing* branch via `git worktree add <path> <branch>` with no `-b` — confirmed this resumes an existing branch cleanly rather than creating a duplicate). Two confirmations of prior lessons, one new one:
  1. **Worktree isolation prevented conflicts again, including for a rebase/merge of an already-pushed branch, not just fresh work.** No races, no HEAD confusion, `git merge origin/main --no-edit` ran safely alongside ~14 other agents' concurrent worktrees in the same repo.
  2. **The "additive-only, decouple from unmerged sibling PR" strategy from the #17/#19 entry above paid off exactly as designed**: merging `origin/main` (containing #17's now-merged `main.bicep` changes) into the `squad/19-...` branch produced **zero conflicts in `infra/main.bicep`** — only `infra/README.md` conflicted (two independently-added doc sections + a module-layout list line), which is low-risk prose easily combined by hand. This is strong validation that "only one open PR edits `main.bicep`'s structure at a time, siblings stay additive-only" is the right standing rule for this repo, not a one-off.
  3. **New pattern worth reusing: let the module grant its own cross-resource RBAC via `existing` resource references instead of bubbling principal IDs back up through `main.bicep` parameters.** `function-app.bicep` already accepted `eventHubNamespaceResourceId`/`keyVaultName` and internally declared `existing` Event Hub namespace / Key Vault resources to scope its own "Data Receiver"/"Secrets User" role assignments. This meant wiring it into `main.bicep` was a **one-way dependency only** (`functionApp` module reads `eventHub`/`keyVault` outputs) — no reverse cross-wire of `functionApp.outputs.functionAppPrincipalId` back into `eventHub.receiverPrincipalIds`/`keyVault.readerPrincipalIds` was needed, sidestepping the circular-reference problem that pattern would otherwise create in a single template. Worth defaulting to this "module grants itself access to things it's given a resource ID for" shape for any future module that needs to read/write a sibling resource, rather than the two-phase principal-ID-bubbling pattern used by `key-vault.bicep`'s `readerPrincipalIds`.
