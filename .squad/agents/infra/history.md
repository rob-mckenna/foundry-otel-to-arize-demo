- 2026-10-03: Delivered Milestone 4's infra-scripting track, #22 (end-to-end deployment validation script, PR #104) and #23 (demo cleanup/teardown script, PR #111), each in its own dedicated worktree (`.worktrees/infra-22`, `.worktrees/infra-23`), both removed cleanly after their PRs opened. Several new, broadly reusable findings:
  1. **`az` CLI is actually *installed* in this sandbox, not absent** (`C:\Program Files\Microsoft SDKs\Azure\CLI2\wbin\az.cmd`) — contradicting the Milestone 1/2 assumption that it was simply missing. Every invocation (e.g. `az account show`) still fails, but with a Python traceback from the documented `PermissionError` reading the cached profile at `~/.azure/azureProfile.json`, not a "command not found" error. **Any future script that shells out to `az` must handle "present but broken," not just "absent"** — check for a clean, parseable response, not just binary presence, before trusting any `az` output.
  2. **New critical PowerShell gotcha, found while smoke-testing #23's teardown script against the broken `az`:** under `$ErrorActionPreference = 'Stop'` (set script-wide, as both new scripts do for fail-fast behavior), piping a native command's merged stderr into the success stream via `2>&1` (e.g. `$raw = & az @args 2>&1`) causes each merged `ErrorRecord` to throw as a **terminating** error the instant it's produced — not a catchable/ignorable warning — even though `2>$null` alone would have suppressed it silently. This bypasses a script's own custom fail-reporting/summary logic entirely and crashes with a raw `NativeCommandError`. **Fix pattern, now used throughout `teardown-deployment.ps1`:** wrap every native `az` call in a small helper (`Invoke-AzJson` for JSON-returning calls, `Invoke-AzCommand` for display-only calls) that temporarily sets `$ErrorActionPreference = 'Continue'` for just that call (restored in a `finally` block), captures `$LASTEXITCODE`, and — for JSON calls — wraps `ConvertFrom-Json` in its own try/catch returning `$null` on any parse failure. **This is a standing pattern any future script in this repo that shells out to `az`/`gh`/other native CLIs under a `Stop`-preference script should reuse from day one**, rather than rediscovering it under a live smoke test.
  3. **Secondary PowerShell gotcha:** `($collection | Where-Object {...}).Count` (or any pipeline result assigned directly to a variable) returns `$null`, not `0` or `1`, when the filtered result is a single scalar `PSCustomObject` rather than an array — `.Count` isn't a property PowerShell adds to a bare single object the way it auto-adds it to arrays/collections. This produced blank "Passed:"/"Failed:" counts in a summary table until every such count expression was wrapped in `@(...)` first (e.g. `@($results | Where-Object Pass).Count`). Apply this defensively any time a filtered-then-counted pipeline result could plausibly be 0, 1, or many items.
  4. **Worktree isolation discipline slipped once during #22, then was caught and recovered.** Despite the Milestone 1/2 lesson being well understood, `infra/scripts/validate-deployment.ps1` and an `infra/README.md` edit were initially authored directly in the shared main checkout instead of `.worktrees/infra-22`. Recovery procedure (reusable if this happens again): copy the new/untracked file into the correct worktree, `git diff` the modified-tracked-file's change into a patch, `git checkout -- <path>` to revert the main checkout back to clean, then `git apply <patch>` inside the worktree. No corruption resulted, but this confirms the main checkout being writable and "nearby" during worktree-based work is a real, recurring slip risk — worth a conscious double-check of `$PWD`/`git rev-parse --show-toplevel` before the *first* file write of any worktree-isolated task, not just at task start.
  5. `az`/`bicep` CLI remained the same shared blocker documented above for both #22 and #23 — both scripts were validated via `[System.Management.Automation.Language.Parser]::ParseFile` (0 errors) plus a Windows PowerShell 5.1 smoke test of their failure/degraded paths (not a live deploy or live teardown), explicitly flagged in both PRs' "Tests Performed"/"Current Limitations" sections as requiring a real-Azure validation pass before demo day. Smoke-testing under PS 5.1 again required the already-documented 3-arg-`Join-Path`-to-2-arg-chained substitution, since both scripts (consistent with `validate-naming.ps1`) target `pwsh`/PowerShell 7, and the `pwsh.exe` present in this sandbox is only a non-functional Windows Store execution-alias stub.
