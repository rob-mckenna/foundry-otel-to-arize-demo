Two environment learnings worth remembering for next time:
  1. **The shared working-copy concurrency hazard is real and destructive.** This repo's working directory is used concurrently by multiple squad agents (Lead, Scribe, etc.) who `git checkout` different branches between my tool calls, which silently moved HEAD out from under me mid-task and caused at least one commit to land on the wrong branch. Fix: use `git worktree add .worktrees\<name> -b <branch> origin/main` (worktrees must live *inside* the repo tree — paths outside it hit sandbox `Permission denied`) for every branch touched, and always branch from a freshly-fetched `origin/main`, never the shared local `main` (which can silently drift/diverge from a concurrent agent's unpushed commit). Do all git/file operations for that branch from inside its dedicated worktree directory, never the main checkout.
  2. **`gh`/git in this environment lacks the `workflow` OAuth scope** — pushing any `.github/workflows/*.yml` file is rejected (`refusing to allow an OAuth App to create or update workflow ... without 'workflow' scope`). When a CI-wiring acceptance criterion can't be met for this reason, strip the workflow file and document the equivalent manual pre-merge step instead (most issue acceptance criteria in this repo already anticipate that fallback explicitly).
  3. `az` CLI and a standalone `bicep` binary are both unusable in this sandbox (`az` hits a `PermissionError` reading the cached profile at `~/.azure/azureProfile.json`; no `bicep.exe` is installed) — every Bicep PR in this milestone had to be validated by manual syntax review only, with `az bicep build` / `az deployment group what-if` / live deploy+teardown flagged as a reviewer action item in "Current Limitations" rather than run directly.
- 2026-10-03: Consolidated the 4 remaining Milestone 1 infra PRs (#69 App Insights, #71 Key Vault, #72 naming/tagging, #74 networking) into main one at a time, in that order, after they all drifted from the same pre-#66 base and each had independently rewritten `infra/main.bicep` end-to-end (some even "carried forward" a full imagined snapshot of sibling issues' modules, e.g. #72/#74 branches already contained their own copies of #15/#16/#18's module files). Two lasting lessons:
  1. **Parallel branches off the same base editing the same IaC entry-point file (`main.bicep`) is the root cause, and it compounds.** Every `module`/`param`/`output` block landed as an "add/add" conflict at merge time even for file paths that were never touched by more than one PR, because git had no common ancestor content to diff against. The actual *content* conflicts were almost always trivially combinable (verified via `git diff <mainBlobSHA> <branchBlobSHA> -- <path>` before touching anything) — the pain was 100% structural/mechanical, not semantic. Going forward: either (a) require every infra PR to branch from a freshly-fetched `main` *after* the previous infra PR in the queue has merged (serialize the queue, don't parallelize), or (b) adopt an explicit convention that only one PR at a time "owns" `main.bicep`'s structure (adding new `module`/`output` blocks) and all others are strictly additive new files under `infra/modules/` with zero `main.bicep` edits, reconciled into `main.bicep` by whoever currently owns it.
  2. **A second agent's "fix" merge can silently regress a just-merged PR if the two merges race within seconds.** PR #70 (ADR docs, unrelated issue #13) merged 4 seconds after PR #69 and its own conflict-resolution commit — reasonably, from its branch's point of view — reset `infra/main.bicep`/`main.parameters.json`/`README.md` and deleted `infra/modules/app-insights.bicep` entirely, believing it was removing "accidental cross-contamination" from a shared non-worktree checkout, when in fact that content was PR #69's legitimate, already-merged change. I had to re-detect this by independently diffing `origin/main`'s tree against the PR's own merge commit (not trusting "already merged" status) and push a direct restoring commit to `main` before continuing the queue. Recommendation: after merging any infra PR, re-verify `origin/main`'s actual tree contents (not just PR merge status) before starting the next PR's conflict resolution — another concurrent agent may have merged in between and silently clobbered it.
